## 第15章　組織への導入と成熟度

要求管理は、個別プロジェクトの上流工程ではなく、組織が持つべき能力です。この章では、組織能力にするための要素、部門ごとの役割分担、6つの導入ステップ、5段階の成熟度モデル、そして外部委託時の注意点を学びます。

:::message
**この章で学ぶこと**

- 要求管理を組織能力にするための要素を挙げられる
- 要求管理の成果物が「組織の知識資産」である理由を説明できる
- 部門・担当ごとの主な責任を説明できる
- 導入の6ステップと「小さく始める」理由を理解する
- 要求管理の成熟度5段階を区別できる
- 調達・委託時に明確にすべき事項を挙げられる

**キーワード**：組織能力、知識資産、役割分担、導入ステップ、小さく始める、テーラリング、成熟度モデル、属人型、AI協働型、調達・委託

**優先して読む人**（原典「表1」より）　◎ 優先：経営層、事業部門、業務改革担当、DX推進部門、IT・情報システム部門、AI開発・利用部門、法務・コンプライアンス部門、調達部門／〇 次点：開発者、データ部門、セキュリティ部門、監査部門、行政機関の制度設計担当者
:::

### 15.0 第5部の見取り図

AI時代の要求管理は、事業、業務、データ、AI、ソフトウェア、法令・標準、社内規則、運用、監査をつなぎ、変化に対応しながら価値を生み続けるための**組織能力**です。属人的な作業にせず、標準的なプロセス、成果物、役割分担、成熟度の考え方を整えます。すべてのプロジェクトで大量の文書を作る必要はありませんが、目的、要求、要件、データ、AI、ルール、評価、変更管理を最低限確認できる状態にしておくことが重要です。第5部では、組織への導入（本章）と主な成果物（第16章）を扱います。

### 15.1 要求管理を組織能力にする

| 要素 | 内容 |
|---|---|
| 標準プロセス | 獲得、分析、仕様化、評価、管理の流れを定める |
| 標準テンプレート | 要求定義書、要件定義書、要求管理台帳、AI要求管理等の型を用意する |
| 役割分担 | 事業、IT、AI、データ、法務、監査の責任を明確にする |
| レビュー体制 | 要求の妥当性、実現可能性、リスクを確認する |
| ツール活用 | 要求管理、モデリング、変更管理を支援する |
| 教育 | 要求工学、AI、データ、ルール要求の基礎を学ぶ |
| 改善サイクル | 運用後のフィードバックを変更要求に反映する |

#### 要求管理の成果物は「組織の知識資産」

要求管理の成果物には、組織が何を重視し、どの業務をどう行い、どのデータを使い、どのルールを守り、どのリスクを避け、どんな品質を求めているかが集約されます。つまり要求管理は、業務知識、顧客理解、データ理解、技術知識、ルール、リスク管理、運用経験を結びつける**知識資産づくり**でもあります。

| 知識資産がない組織 | 要求が組織的に管理されている組織 |
|---|---|
| プロジェクトのたびに一から関係者に確認し、資料を探し、暗黙知を掘り起こす。同じ議論の繰り返し、抜け漏れ、異動による知識喪失 | 過去の要求、判断理由、業務ルール、データ定義、評価基準、変更履歴を再利用し、新規プロジェクト、AI活用、M&A後の統合、法令改正対応を迅速に進められる |

:::message
**ポイント：競争力の源泉は「要求の設計力」**

企業の競争力は、ソフトウェアやAIモデルそのものより、**何を解くべき課題と捉え、どの業務をどう設計し、どのデータを使い、どんな品質や体験を実現するか**という要求の設計力に左右されます。同じAIやクラウドを使っても、目的・要求・データ・評価基準が優れていなければ価値は生まれません。逆に要求管理が優れていれば、既存のOSSやSaaS、AIサービスの組み合わせでも組織固有の価値を生み出せます。
:::

AI時代には、過去の要求定義、台帳、業務フロー、データ定義、規則、障害記録、監査指摘、改善履歴を**AIに参照させる**ことで、たたき台作成、抜け漏れ確認、類似事例検索、影響分析を支援させることもできます。組織能力化とは、テンプレートを作ることではなく、組織の知識を**再利用可能で、更新可能で、人とAIがともに活用できる形**にすることです。

### 15.2 役割分担

良い要求を定義するために確認すべきことは多岐にわたり、IT部門やベンダーだけでは非常に困難です。

| 部門・担当 | 主な責任 |
|---|---|
| 経営層・事業責任者 | 目的、価値、優先度、投資判断を示す |
| 業務部門 | 現場要求、業務ルール、例外処理を示す |
| IT部門 | システム要件、実装可能性、運用性を確認する |
| AI担当 | AI利用目的、評価、監視、更新条件を整理する |
| データ担当 | データ定義、品質、出典、利用条件を確認する |
| 法務・コンプライアンス | 法令、標準、契約、社内規則との整合を確認する |
| セキュリティ担当 | リスク、アクセス制御、ログ、インシデント対応を確認する |
| 監査担当 | 証跡、評価方法、説明責任を確認する |
| 調達・契約担当 | 委託先、SLA、責任分担、契約条件を整理する |
| 利用者・現場代表 | 使いやすさ、現実性、業務適合性を確認する |

重要なのは、各部門が自分の専門領域だけを見るのではなく、**要求・データ・AI・ルール・運用がどうつながるかを共同で確認する**ことです。

#### ✅ 確認問題

**問1**　「データ定義、品質、出典、利用条件を確認する」のは、どの部門・担当の主な責任ですか。

- A. 調達・契約担当
- B. 監査担当
- C. データ担当
- D. 利用者・現場代表

:::details 答えと解説
**正解：C**

データの定義・品質・出典・利用条件の確認はデータ担当の主な責任です。ただし各部門は共同でつながりを確認します。
:::

### 15.3 導入ステップ

最初からすべての成果物やトレーサビリティを網羅的に整備しようとしないことが重要です。体制や経験が不十分な段階で管理対象を広げすぎると、**文書作成や管理作業自体が目的化し、形骸化**するおそれがあります。まずは主要な要求とその根拠、関連する要件や検証方法、変更履歴を確認できる状態にし、試行と改善を繰り返しながら段階的に広げます。

1. **現状把握**：要求定義書・台帳の有無、変更管理の方法、レビュー体制、モデリングの利用状況、AIやデータ要求の扱いを確認する。
2. **標準テンプレートの整備**：主要な要求と根拠を一覧で管理できる**簡易な台帳から**始めるのも有効。必要に応じてAI・データ・ルールの項目を追加する。社内ルールの構造化もMarkdownなど軽量な方法から。
3. **小規模なプロジェクトで試行**：一斉展開せず、**小規模で低リスク、試行錯誤しやすい**プロジェクトから。効果と現場の負担を検証し、改善しながら重要なプロジェクトへ広げる。
4. **レビューと教育**：試行結果でテンプレートやプロセスを改善し、各部門向けに教育する。経験が浅い組織では、対話型AIでヒアリングの質問提示や抜け漏れ確認を支援させ、実務経験を積む。
5. **ツール活用を進める**：要求管理ツール、モデリングツール、ドキュメント管理、AI支援ツールで、要求・要件・モデル・データ・テスト・ログの対応関係を管理しやすくする。
6. **組織標準として定着させる**：組織標準、調達要件、開発標準、AI利用ルール、監査項目に反映し、継続的な組織能力にする。

:::message
**補足：どれくらいの工数をかけるべきか（テーラリング）**

一律に最適な比率はありませんが、参考として、システムズエンジニアリング活動は総プロジェクトコストの10〜14%程度がROIとしてよいとされ、そのうち要求工学は2%程度とする研究もあります。ハンドブックは、要求定義を含む広義の要求管理の初期的な目安として**総コストの2〜5%程度**を出発点とし、プロジェクトの特性に応じて調整することを勧めています。ただし最適値の保証ではなく、要求起因の手戻りや変更頻度などの実績を見ながら見直します。AIを扱うからといって一律に増やす必要はなく、実際に必要な活動から見積もります。
:::

#### ✅ 確認問題

**問1**　要求管理を組織に導入する際、最初から全成果物とトレーサビリティを網羅的に整備しようとすることのリスクとしてハンドブックが指摘しているものはどれですか。

- A. コストが下がりすぎる
- B. 文書作成や管理作業自体が目的化し、形骸化するおそれがある
- C. AIが使えなくなる

:::details 答えと解説
**正解：B**

小さく始め、試行と改善を繰り返しながら段階的に管理水準を上げるのが現実的です。
:::

### 15.4 成熟度モデル

| レベル | 状態 | 目指す姿 |
|---|---|---|
| Lv.1 属人型 | 担当者の経験に依存し、文書や粒度がばらばら | 最低限の文書化を始める |
| Lv.2 文書化型 | 要求定義書はあるが、変更管理やトレーサビリティが弱い | 要求一覧と変更履歴を整備する |
| Lv.3 管理型 | 要求管理台帳、レビュー、変更管理がある | AI・データ・ルール要求を明示する |
| Lv.4 モデル活用型 | 業務、データ、システム、評価をモデルで接続する | 影響分析や監査に活用する |
| Lv.5 AI協働型 | AIを使って要求抽出、分析、影響分析、改善を継続的に行う | ライブな要求管理を実現する |

:::message
**ポイント：成熟度の上げ方**

- 組織全体で一律に上げる必要はない。**リスクの高い領域、変更頻度の高い領域、AI活用の効果が大きい領域**から優先する。
- AIの活用は成熟度の高い組織だけのものではない。経験が少ない組織でも、対話型AIによるヒアリング支援や要求候補の整理から始められる。Lv.5の「AI協働型」は、個別の活用にとどまらず、**要求管理プロセス全体にAIを継続的に組み込み、人とAIが協働して管理・改善する段階**を指す。
:::

### 15.5 調達・委託時の注意点

要求定義を曖昧なまま委託すると、後工程で大きな手戻りや責任分担の問題が生じます。少なくとも次を明確にします。

- 目的と成果／対象範囲／役割分担／**要求定義の責任**
- データ提供条件／AI利用条件
- 成果物／受入条件／変更管理手順
- セキュリティ要件／法令・標準・社内規則への対応
- 運用後の保守・監視
- 知的財産・成果物の扱い／ログ・証跡の扱い

AI開発では、**モデル、プロンプト、学習データ、評価データ、ログ、改善履歴**が重要な資産になります。これらが誰の管理対象で、どの範囲で利用できるかを、契約や要求定義で明確にしておく必要があります。

### 第15章のまとめ

:::message
- 要求管理は**組織能力**。標準プロセス、テンプレート、役割分担、レビュー、ツール、教育、改善サイクルで支える。
- 成果物は組織の**知識資産**であり、競争力の源泉は「要求の設計力」。人とAIが共に活用できる形にする。
- 経営層から現場代表まで各部門が責任を持ち、**つながりを共同で確認**する。
- 導入は**現状把握 → テンプレート → 小規模試行 → レビューと教育 → ツール活用 → 組織標準化**。小さく始め、形骸化を避ける。工数の目安は総コストの2〜5%程度から調整。
- 成熟度は**属人型 → 文書化型 → 管理型 → モデル活用型 → AI協働型**。高リスク・高変更頻度・AI効果大の領域から上げる。
- 委託時は要求定義の責任、データ・AI利用条件、受入条件、変更管理、知財、ログを明確にし、AI関連資産の管理主体も決める。
:::

**問1**　要求管理の成果物を「組織の知識資産」と捉えることの効果として最も適切なものはどれですか。

- A. プロジェクトごとに一から関係者に確認できるようになる
- B. 担当者の異動が不要になる
- C. 文書の量が増えて監査が厳しくなる
- D. 過去の要求、判断理由、業務ルール、データ定義、変更履歴を再利用し、新しい取り組みを迅速に進められる

:::details 答えと解説
**正解：D**

知識資産が整備されていれば、同じ議論の繰り返しや異動による知識喪失を防げます。
:::

**問2**　ハンドブックが考える企業の競争力の源泉として最も近いものはどれですか。

- A. 最新のAIモデルを導入していること
- B. 何を課題と捉え、業務・データ・品質をどう設計するかという要求の設計力
- C. 開発者の人数が多いこと
- D. 社内規則のページ数が多いこと

:::details 答えと解説
**正解：B**

同じAIやクラウドを使っても、目的・要求・データ・評価基準が優れていなければ十分な価値は生まれません。
:::

**問3**　「目的、価値、優先度、投資判断を示す」のは、どの部門・担当の主な責任ですか。

- A. IT部門
- B. 法務・コンプライアンス
- C. 経営層・事業責任者
- D. 監査担当

:::details 答えと解説
**正解：C**

経営層・事業責任者は、目的と価値、優先度、投資判断を示します。
:::

**問4**　導入ステップの順序として正しいものはどれですか。

- A. ツール導入 → 現状把握 → 組織標準化 → 小規模試行
- B. 現状把握 → テンプレート整備 → 小規模試行 → レビューと教育 → ツール活用 → 組織標準化
- C. 組織標準化 → テンプレート整備 → 全社一斉展開 → 教育
- D. 小規模試行 → 組織標準化 → 現状把握 → ツール導入

:::details 答えと解説
**正解：B**

現状を把握し、簡易なテンプレートで小さく試し、改善と教育を経て、ツール活用と組織標準化へ進みます。
:::

**問5**　最初に試行するプロジェクトの選び方としてハンドブックが勧めるものはどれですか。

- A. すでに完了したプロジェクト
- B. 小規模でリスクが低く、試行錯誤しやすいプロジェクト
- C. 実際の業務とは関係のない架空のプロジェクト
- D. 最も重要で大規模なプロジェクト

:::details 答えと解説
**正解：B**

効果と現場の負担を検証しやすい小規模・低リスクのプロジェクトから始め、段階的に広げます。
:::

**問6**　成熟度「Lv.3 管理型」の状態として正しいものはどれですか。

- A. 要求定義書はあるが、変更管理やトレーサビリティが弱い
- B. 業務、データ、システム、評価をモデルで接続している
- C. 要求管理台帳、レビュー、変更管理がある
- D. 担当者の経験に依存し、文書や粒度がばらばら

:::details 答えと解説
**正解：C**

管理型は台帳・レビュー・変更管理がある段階で、次はAI・データ・ルール要求の明示を目指します。
:::

**問7**　「Lv.5 AI協働型」の説明として正しいものはどれですか。

- A. AIを一度でも使ったことがある段階
- B. 要求管理プロセス全体にAIを継続的に組み込み、人とAIが協働して管理・改善を行う段階
- C. AIが人間の代わりにすべての要求を承認する段階
- D. Lv.4に到達するまでAIは使ってはいけない

:::details 答えと解説
**正解：B**

AIの活用自体はどの段階からでも始められます。Lv.5はプロセス全体への継続的な組み込みを意味します。
:::

**問8**　AI開発を外部委託する際、契約や要求定義で管理主体と利用範囲を明確にすべきものとしてハンドブックが特に挙げているものはどれですか。

- A. モデル、プロンプト、学習データ、評価データ、ログ、改善履歴
- B. 委託先の社員名簿
- C. 委託先の他の顧客リスト
- D. 委託先のオフィスの所在地

:::details 答えと解説
**正解：A**

AI開発ではこれらが重要な資産になるため、誰の管理対象で、どの範囲で利用可能かを明確にします。
:::

## 第16章　成果物一覧

最終章では、AI時代の要求管理で作る代表的な成果物を一覧で整理し、プロジェクトの規模やリスクに応じた選び方を学びます。最後にハンドブック全体を振り返ります。

:::message
**この章で学ぶこと**

- 要求定義書と要求管理台帳の位置づけと、二重管理を避ける方法を説明できる
- AI時代の代表的な成果物とその意義を挙げられる
- プロジェクトの規模・AI利用・法令関連・リスクに応じて成果物を選べる
- ハンドブック全体の要点を説明できる

**キーワード**：成果物、要求定義書、要求管理台帳、正本、要件定義書、AI要求管理、ルール要求一覧、トレーサビリティ表、変更管理記録、構造化文書、テーラリング

**優先して読む人**（原典「表1」より）　◎ 優先：事業部門、業務改革担当、DX推進部門、IT・情報システム部門、AI開発・利用部門／〇 次点：開発者、法務・コンプライアンス部門、監査部門、行政機関の制度設計担当者
:::

### 16.1 要求定義書と要求管理台帳の位置づけ

成果物はプロジェクトの規模やリスクに応じて選択し、すべてを必ず作る必要はありません。ただし、**目的、要求、要件、データ、AI、ルール、評価、変更管理を確認できる最低限の成果物**は必要です。なお、ハンドブックでいう「〜書」「〜台帳」は紙ではなく、**デジタルデータでの管理**が前提です。

#### 要求定義書

**要求定義書**とは、要求とその背景、根拠、発生源、優先度、関連要求、検証方法、関連する図・表・モデルなどを、関係者が体系的に確認できる形で整理した**文書またはビュー**です。個々の要求の情報に加え、複数の要求にまたがる業務フロー、ユースケース、データモデルなども含めて、要求定義の全体像を示します。

独立した文書として作る必要は必ずしもありません。要求の情報が台帳、業務フロー、ユースケース、データ定義、受入条件などに分かれていても、**要求IDなどで相互の関係を追跡でき、関係者が必要な情報を確認できる**なら、それら全体を要求定義書に相当するものとして扱えます。

#### 二重管理を避ける

:::message
**ポイント：正本を決めて、他方は参照する**

要求定義書と要求管理台帳の両方を作るなら、同じ情報を重複管理しないようにします。要求文、優先度、状態、版、変更履歴などについて**正本となる管理対象**を決め、他方からは参照・リンク・自動生成で使います。

例：個々の要求とその管理属性は**要求管理台帳を正本**とし、要求定義書には台帳では表現しにくい**説明文、業務フロー、図、モデル、意思決定の経緯**を整理する。両者は要求IDで対応づける。
:::

#### ✅ 確認問題

**問1**　要求定義書と要求管理台帳の両方を作成する場合の管理方法としてハンドブックが勧めるものはどれですか。

- A. 項目ごとに正本を決め、他方は参照・リンク・自動生成で利用し、要求IDで対応関係を明確にする
- B. 要求管理台帳は作らず、要求定義書だけにする
- C. 同じ情報を両方に書き、定期的に手作業で突き合わせる

:::details 答えと解説
**正解：A**

二重管理は不整合の原因になります。正本を決め、IDで対応づけるのが基本です。
:::

### 16.2 AI時代の代表的な成果物

| 成果物 | 意義 | 概要 |
|---|---|---|
| 目的・ミッション整理 | 何のために行うかを明確にする | 事業目的、業務目的、社会的価値、成功指標を整理する |
| ステークホルダー一覧 | 関係者と責任を明確にする | 利用者、業務部門、IT、AI、データ、法務、監査等を整理する |
| 要求一覧 | 実現したいことを整理する | 要望から抽出した要求を分類し、優先度や根拠を付ける |
| 要求定義書 | 要求と関連情報を体系的に確認できるようにする | 要求、根拠、発生源、優先度、関連要求、検証方法と関連する図・表・モデル。個別成果物をIDで関連付ける構成でもよい |
| 要件定義書 | 実現すべき事項を合意する | 機能、非機能、AI、データ、ルール、運用、評価を記述する |
| 業務フロー | 業務の流れを可視化する | 作業手順、承認、判断、例外処理、責任者を示す |
| データ定義 | データの意味と品質を明確にする | 項目、定義、出典、形式、品質、利用条件を整理する |
| AI要求管理 | AIの使い方と管理方法を明確にする | 利用目的、入力、出力、人間の関与、評価、監視、更新を定義する |
| ルール要求一覧 | 法令・標準・社内規則との関係を示す | 外部要件・社内ルールを業務やシステム要件へ展開する |
| 機能要件一覧 | システムが提供すべき機能を示す | 機能、処理、入出力、振る舞いなどを整理する |
| 非機能要件一覧 | 満たすべき品質条件を明確にする | 性能、可用性、セキュリティ、保守性、拡張性など |
| 受入条件 | 完了判断を明確にする | 要件が満たされたことを確認する基準を定める |
| トレーサビリティ表 | 変更影響と説明責任を支える | 目的、要求、要件、設計、テスト、ログの対応を示す |
| 要求評価・妥当性確認結果 | 評価結果を記録する | 要求一覧に紐づけて、要求ごとの評価結果と次アクションを記述する |
| 要求管理台帳 | 要求を継続的に管理する | 要求ID、状態、優先度、変更履歴、検証方法を管理する |
| 変更管理記録 | 変更の理由と影響を残す | 変更要求、影響分析、承認、対応結果を記録する |
| 運用・監視計画 | 運用後の改善につなげる | 監視項目、ログ、評価頻度、責任者、改善手順を整理する |
| 構造化文書 | AIやツールで活用しやすくする | Markdown、XML、Akoma Ntoso型構造、ReqIF等で管理する |

#### 規模やリスクに応じた選び方

成果物は多ければよいわけではありません。重要なのは、**関係者が合意でき、実装に使え、評価でき、変更時に参照できる**ことです。

| プロジェクトの特性 | 成果物の組み合わせ |
|---|---|
| 小規模 | 目的整理、要求一覧、要求管理台帳、要件定義書、受入条件 |
| ＋AIを利用する | ＋AI要求管理、データ定義 |
| ＋法令・標準・社内規則に関係する | ＋ルール要求一覧、トレーサビリティ表 |
| 高リスク | 業務フロー、データモデル、AI利用モデル、リスク評価、監査証跡、変更管理記録まで整備 |

:::message alert
**注意：作って終わりにしない**

成果物は運用後も、業務・制度・利用環境の変化や新たな知見に応じて、**変更理由と影響を明確にしたうえで見直します**。要求定義書・要件定義書、要求管理台帳、データ定義、AI要求管理、ルール要求一覧は**変更管理の対象**です。
:::

#### ✅ 確認問題

**問1**　小規模なプロジェクトでAIを利用する場合、基本の成果物に加えるべきものとしてハンドブックが挙げているものはどれですか。

- A. ルール要求一覧とトレーサビリティ表
- B. 監査証跡とリスク評価
- C. AI要求管理とデータ定義

:::details 答えと解説
**正解：C**

小規模の基本セット（目的整理、要求一覧、台帳、要件定義書、受入条件）に、AIを使う場合はAI要求管理とデータ定義を加えます。
:::

### おわりに ― ハンドブック全体の振り返り

最後に、ハンドブックが繰り返し伝えてきた要点を確認しましょう。

1. **AI時代の要求管理は、開発前に一度だけ行う作業ではない。** 目的を確認し、要求を獲得・分析・仕様化し、モデル化し、評価し、実装へ接続し、運用後のデータをもとに改善する**循環的な活動**である。
2. **要求管理は個人の職人芸ではなく、組織能力として整備するもの。** 標準プロセス、成果物、役割分担、テンプレート、要求管理台帳、変更管理、教育、ツール活用を組み合わせて品質を高める。
3. **AIに要求管理を任せるのではない。** AIを活用しながら、**人間が目的・価値・リスク・制約・評価を明確にし**、要求を継続的に管理・更新できる状態を作ることが重要である。

要求管理を組織能力として高めることが、変化に強い企業と社会をつくる基盤になります。ここまでの学習を、身近な業務やプロジェクトで要求管理を見直す第一歩につなげてください。

### 第16章のまとめ

:::message
- 成果物は規模とリスクで選ぶ。ただし目的・要求・要件・データ・AI・ルール・評価・変更管理を確認できる最低限は必要。デジタル管理が前提。
- **要求定義書**は文書またはビュー。個別成果物をIDで関連付けた全体でもよい。台帳との**二重管理を避け、正本を決める**。
- 代表的な成果物：目的整理、ステークホルダー一覧、要求一覧、要求定義書、要件定義書、業務フロー、データ定義、AI要求管理、ルール要求一覧、機能・非機能要件一覧、受入条件、トレーサビリティ表、評価結果、台帳、変更管理記録、運用・監視計画、構造化文書。
- 小規模は5点セットから、AI利用・法令関連・高リスクに応じて追加。成果物は**変更管理の対象**として運用後も見直す。
- 全体の結論：**循環的な活動**、**組織能力**、そして**人が目的と価値を握り、AIを使いこなす**。
:::

**問1**　ハンドブックにおける「要求定義書」の説明として正しいものはどれですか。

- A. 要求と背景・根拠・関連する図やモデルなどを体系的に確認できる文書またはビューで、個別成果物をIDで関連付けた全体として扱うこともできる
- B. 要求管理台帳の別名である

- C. 要求IDの採番ルールだけ
- D. 要求の版と変更履歴

:::details 答えと解説

管理属性は台帳を正本とし、要求定義書には説明や図、経緯などを整理する方法があります。

**問3**　成果物「AI要求管理」で定義する内容として正しいものはどれですか。

- A. 開発者の勤務時間
- B. 機能要件の一覧

- D. AIベンダーの選定理由のみ

:::details 答えと解説
**正解：C**

AI要求管理は、AIの使い方と管理方法を明確にする成果物です。
:::

**問4**　「目的、要求、要件、設計、テスト、ログの対応を示し、変更影響と説明責任を支える」成果物はどれですか。

- A. 受入条件

- A. 業務フローとデータモデル
- B. ルール要求一覧とトレーサビリティ表
- C. 運用・監視計画のみ
- D. AI要求管理とデータ定義

- B. 成果物は多ければ多いほど品質が高い
- C. 関係者が合意でき、実装に使え、評価でき、変更時に参照できることが重要で、運用後も変更管理の対象として見直す
- D. 一度承認された成果物は変更してはならない

量ではなく使えることが大事です。成果物は運用後も見直されます。

**問7**　ハンドブック全体の結論として最も適切なものはどれですか。

- A. 要求管理は開発前に一度だけ丁寧に行えばよい

- C. 要求管理は優秀な担当者の職人芸に任せるのが最も効率的である
- D. AIの進化により要求管理は不要になる

:::details 答えと解説
**正解：B**

AIに任せるのではなく、AIを使いこなすために要求管理の力がより重要になる、というのがハンドブックのメッセージです。
